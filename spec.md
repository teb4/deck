# Полная спецификация Deck

## 0. Назначение

**Deck** — это не просто текстовый редактор с поддержкой LLM. Это язык транзакционного редактирования, где единственным предполагаемым автором команд является LLM, а не человек.

Deck — редактор текстовых файлов, спроектированный специально для LLM. Модель никогда не видит и не правит файл напрямую — она получает от редактора пронумерованные фрагменты и отвечает пакетом («колодой») команд, который применяется к файлу атомарно, за один проход.

Дизайн опирается на принцип пакетной обработки перфокарт 1960-х: программа готовилась целиком заранее (колода карт), программист не видел файл — и не мог его прямо исправить — мониторов не было; считывающее устройство не могло «посмотреть и поправить» — только применить пакет целиком или отвергнуть его. LLM сегодня находится в точно таком же положении: она не видит файл «вживую», формулирует правку целиком в одном ответе и не может на лету исправить то, что уже сгенерировала.

Для контроля версий и целостности во всех операциях используется алгоритм хэширования **xxhash (xxh64)**.

Из этого вытекают сквозные решения:

- **Адресация по номерам строк, а не по содержимому** — модель не обязана формулировать уникальный фрагмент текста.
- **Атомарность колоды** — вся колода применяется целиком или не применяется вовсе.
- **Криптографическая защита от гонок версий (`<rev>`)** — жесткая привязка к конкретному хэшу xxhash файла на момент чтения.
- **Разделение потоков** — модификация файла (Deck) и создание нового файла (`CREATE` из stdin) разделены на уровне CLI.
- **Позиционно-лексическое распознавание команд** — команда определяется положением в строке (нулевая колонка) **и** наличием строгого зарезервированного ключевого слова.

## 1. Мотивация (Почему традиционные инструменты не работают)

Разработка Deck продиктована фундаментальным когнитивным несоответствием между тем, как работают современные LLM, и тем, как устроены традиционные текстовые редакторы (`vim`, `nano`) и CLI-утилиты патчинга (`sed`, `awk`, `patch`).

При использовании LLM в роли AI-агента для модификации кода выявились критические проблемы, которые Deck призван решить:

- **Антипаттерн полной перезаписи (The Rewrite Anti-Pattern).** При использовании `sed` или `patch` модели регулярно сталкиваются с ошибками экранирования спецсимволов, сложным синтаксисом регулярок и неточным матчингом контекста. Столкнувшись с невозможностью применить точечный патч, LLM «сдается» и генерирует весь файл целиком заново. Это колоссальный расход токенов, риск исчерпания контекста и уничтожение параллельных изменений.
- **Когнитивное несоответствие (Интерактивность vs Пакетная обработка).** LLM — это авторегрессионный генератор текста. Она не может «нажать Backspace» или интерактивно исправить опечатку в синтаксисе CLI-команды, как это делает человек. Пакет команд должен быть сформирован целиком и применен атомарно.
- **Экономика токенов.** Встроенный в редакторы поиск по регулярным выражениям требует загрузки файла в контекст. Делегирование поиска специализированным утилитам позволяет работать с файлами на десятки тысяч строк без исчерпания контекстного окна.

## 2. Симбиоз с экосистемой (Unix-way и поиск)

Deck намеренно не реализует встроенный поиск по содержимому (например, адресацию по регулярным выражениям `/regex/`, как в `sed` или `ed`). Согласно философии Unix-way, задача обнаружения кода делегируется внешним, высокопроизводительным инструментам.

**Типовой цикл работы (Target Workflow) LLM-агента:**

1. **Текстовый поиск (Разведка):** Агент использует `ripgrep` (`rg -n`) для быстрого поиска уникальных строк и получения их точных номеров.
2. **Структурный поиск (AST):** Для поиска полных логических блоков (например, «найди всю функцию `calculate_total` целиком, включая тело») агент использует `ast-grep`. В отличие от текста, `ast-grep` понимает синтаксис языка и возвращает точные граничные строки (`start_line` - `end_line`), которые идеально маппятся на операцию `REPLACE N-M`.
3. **Чтение контекста (GET):** Агент запрашивает у Deck узкий диапазон вокруг цели, чтобы увидеть окружение и зафиксировать `<rev>`.
4. **Применение (APPLY):** Агент формирует колоду с точным адресом и применяет её атомарно.

## 3. Принцип нумерации и Защита контекста

**Нумерация строк** — это то, что редактор возвращает модели, а не то, что модель ему передаёт. Номера появляются только в ответах `GET` и `CREATE`; в самом файле на диске их никогда нет.

Всё, что модель передаёт редактору как новый текст — payload команд `REPLACE`/`INSERT` или поток в `CREATE` — всегда без номеров. Единственный способ узнать актуальные номера строк — прочитать через `GET` или получить их в ответе на `CREATE`.

### Защита от устаревания контекста (Context Drift Protection)

Текущий `<rev>` (хэш xxh64 от содержимого файла) возвращается в ответах. В парадигме LLM-агентов `<rev>` выполняет функцию защиты от устаревания контекста (Stale Context Prevention).

Между чтением файла (`GET`) и генерацией колоды файл на диске мог быть изменен внешними процессами (линтерами, автоформаттерами, IDE). Применение патча к измененному файлу на основе старого контекста разрушительно. Механизм `<rev>` гарантирует, что агент никогда не применит правки вслепую к «призраку» из своей памяти. При ошибке `version conflict` агент обязан выполнить новый `GET` для актуализации снимка.

## 4. Внешняя команда `GET` — чтение

```
deck-editor get <file> <addr>
```

Недеструктивная операция вне колоды. Возвращает запрошенный диапазон строк и текущий `<rev>`.

**Формат вывода:**

```
REV: abc123def456
000001:первая строка
000002e
000003:третья строка
```

- `REV: <hash>` — хэш xxhash текущего состояния файла.
- `NNNNNN:текст` — непустая строка (минимум 6 разрядов).
- `NNNNNNe` — пустая строка (суффикс `e`).
- Для **абсолютно пустого файла** (0 байт) `GET` возвращает только строку `REV: <hash>` без пронумерованных строк.

---

## 5. Внешняя команда `CREATE` — новый файл или полная замена

```
deck-editor create <file> [<rev>]
```

Не является частью колоды. Это внешняя CLI-команда, которая читает содержимое файла напрямую из стандартного потока ввода (`stdin`) до его закрытия (EOF).

**Payload:** весь текст из `stdin`. Он не сканируется на наличие управляющих слов, поэтому маркеры и терминаторы не требуются. Можно безопасно создавать bash-скрипты с `$VAR` и `$END` на нулевой колонке.

`<rev>`: обязателен при перезаписи существующего файла (защищает от гонок версий, так как полная перезапись стирает файл целиком). Если файл не существует, `<rev>` указывать нельзя.

В ответ на успешный `CREATE` редактор возвращает полный нумерованный листинг результата (как `GET`), включая новый `REV` (xxhash).

## 6. Структура колоды (грамматика)

Колода предназначена исключительно для модификации существующего файла.

```
колода         := заголовок тело терминатор
заголовок      := маркер ("DRY" | "DRY_ALL" | "APPLY") <rev>
маркер         := "@" | "$"
тело           := operation+
operation      := replace_op | delete_op | insert_op | insert_head_op
replace_op     := маркер "REPLACE" addr [SKIP] payload
delete_op      := маркер "DELETE" addr                 # СТРОГО без payload, без SKIP
insert_op      := маркер "INSERT" N [SKIP] payload
insert_head_op := маркер "INSERT_HEAD" [SKIP] payload
терминатор     := маркер "END"
```

**Архитектурное назначение терминатора (Guard Clause against Truncation):**
Терминатор — это всегда абсолютная последняя строка (карта) колоды. Его главная задача — детектирование «когнитивного дрейфа» или **обрыва генерации (Max Tokens Cut-off)** LLM. Если модель исчерпала лимит токенов или потеряла контекст, она может просто оборвать генерацию на середине payload.

**Следствие для парсера (Fast-Fail):** Проверка наличия терминатора в конце входной строки — это **самая первая операция** при получении колоды. Если последняя строка не является валидным терминатором, парсер обязан немедленно прервать обработку и вернуть ошибку. Дальнейший парсинг тела колоды (операций) не имеет смысла и строго запрещен, так как колода заведомо неполная (truncated).

Маркер, заданный в заголовке, действует на всю колоду. Смешивание `@` и `$` в пределах одной колоды не допускается.

## Этапы обработки колоды (Deck Processing Pipeline)

Обработка колоды строго разделена на последовательные этапы. Ошибки должны выявляться на максимально раннем этапе (**Fast-Fail**):

### Этап 0. Integrity Check (Проверка целостности, `parser.py`)

*Guard Clause.* Парсер проверяет только последнюю строку переданного текста. Если это не `<marker>END`, парсер немедленно бросает `DeckSyntaxError("deck not terminated by END")`. **Никакой дальнейший парсинг не выполняется.**

### Этап 1. Parsing (Синтаксический анализ, `parser.py`)

Разбиение текста на Header, Operations, Terminator. Проверка соответствия BNF-грамматике (Секция 6).
*Выявляются:* неизвестные команды, отсутствие `<rev>`, несоответствие маркеров, наличие payload у `DELETE`, лишние аргументы у `SKIP`, строки после терминатора.
*Исключение:* `DeckSyntaxError`.

### Этап 2. Validation (Семантическая валидация, `apply.py`)

Проверка адресов и ревизий относительно реального файла на диске.
*Выявляются:* несуществующие строки (`address out of range`), `N > M` в диапазонах, `version conflict`, применение `APPLY` к несуществующему файлу.
*Исключения:* `AddressError`, `VersionConflictError`.

### Этап 3. Application (Применение, `apply.py`)

Непосредственное выполнение операций в памяти и атомарная запись на диск.

## 7. Правило распознавания управляющей строки

Строка признаётся управляющей (командой) **только при одновременном выполнении трёх условий**:

1. Маркер (`@` или `$`) стоит первым символом строки (нулевая колонка).
2. **Сразу за маркером следует строгое зарезервированное ключевое слово** из списка: `DRY`, `DRY_ALL`, `APPLY`, `REPLACE`, `DELETE`, `INSERT`, `INSERT_HEAD`, `END`.
3. Сразу после ключевого слова — конец строки или пробел (разделитель аргументов).

**Фундаментальное следствие:** Сам по себе символ `@` или `$` в нулевой колонке **не является командой**. Если за маркером следует любое другое слово (например, Python-декораторы `@app.route`, `@property`, `@staticmethod`, `@Override`, Java-аннотации или email), парсер автоматически распознает эту строку как обычный **payload** (текст).

Парсер не «пугается» символа `@` в нулевой колонке. Конфликт возникает **только** в том случае, если payload случайно содержит *валидную комбинацию маркера и ключевого слова* (например, вы генерируете документацию по Deck и пишете `@END` как пример текста, или bash-скрипт выводит строку `@REPLACE`).

Строка, не удовлетворяющая условиям, — payload. Отступленный код физически не может быть спутан с командой.

## 8. Заголовок колоды

```
@DRY <rev>      — предпросмотр, возвращает diff (экономия токенов).
@DRY_ALL <rev>  — предпросмотр, возвращает полный нумерованный листинг.
@APPLY <rev>    — применение и запись на диск.
```

`<rev>` — **ОБЯЗАТЕЛЬНЫЙ** 16-символьный хэш xxhash (xxh64) существующего файла.
- Если хэш отсутствует в заголовке, колода отклоняется на этапе **Parsing**.
- Если хэш не совпадает с текущим хэшем файла на диске — колода отклоняется целиком на этапе **Validation** (`version conflict`).

**Примечание:** `<rev>` обязателен при работе с существующими файлами. Это криптографическая гарантия того, что вы применяете правки к тому самому файлу, который читали. Если агент не знает `<rev>`, он обязан выполнить `GET` перед формированием колоды.

## 9. Адресация

```
addr := N | N-M | N-
```

- `N` — одна строка (1-индексация).
- `N-M` — строки с N по M включительно (`N ≤ M`).
- `N-` — от строки N до конца файла.

`INSERT` принимает только одиночный адрес `N`.

`INSERT_HEAD` не принимает адрес (вставка перед строкой 1).

---

## 10. Форматы ответов

### Ответ `DRY` (Diff)

Возвращается в стандартном формате **unified diff** (как `diff -u`), который LLM-агенты распознают идеально.

```
REV: a3f5b7c9d1e2f406 (would be new)
Original: a3f5b7c9d1e2f405 → Modified: a3f5b7c9d1e2f406
--- original
+++ modified
@@ -5,1 +5,2 @@
-старый текст
+новый текст 1
+новый текст 2

Operations applied:
- REPLACE lines 5-5 (1 line replaced with 2 lines)
```

*(Если блок > 50 строк, показывается первые 10, `... скрыто ...`, последние 10).*

### Ответ `DRY_ALL` (Полный листинг)

```
REV: a3f5b7c9d1e2f406 (would be new)
000001:первая строка
000002:вторая строка
...
```

Для **абсолютно пустого файла** `DRY_ALL` возвращает `REV: <hash> (would be new)` и приписку `(Empty file: 0 lines)`.

### Ответ `APPLY`

```
APPLIED successfully
REV: a3f5b7c9d1e2f406 (new)
Operations applied:
- REPLACE lines 5-7 (3 lines replaced with 5 lines)
```

## 11. Обычные операции и модификатор `SKIP`

Несколько операций в колоде выполняются последовательно. Каждая работает с результатом предыдущей (номера строк сдвигаются).

### `@REPLACE <addr>`

Заменяет указанный диапазон строк на payload любой длины (M → N). Файл автоматически расширяется или сжимается.

### `@DELETE <addr>`

Удаляет диапазон строк.

**Грамматика:** Строго не имеет payload и не поддерживает модификатор `SKIP` (см. `delete_op` в Секции 6).

**Этап выявления:** Это синтаксическая ошибка. Парсер обязан прервать обработку и вернуть `ERROR: unexpected payload after DELETE` **на этапе Parsing (Этап 1)** (до чтения целевого файла с диска и до семантической валидации адресов).

### `@INSERT <N>`

Вставляет payload после строки `N`.

### `@INSERT_HEAD`

Вставляет payload в самое начало файла (перед строкой 1).

### Модификатор `SKIP`

Используется **только** в том случае, если payload содержит строки, которые парсер обязан распознать как команды (то есть строки, начинающиеся с `@REPLACE`, `@END`, `@INSERT` и т.д. в нулевой колонке — см. Секцию 7).

Обычные конструкции языков программирования (например, `@app.route`, `@staticmethod`, `@property` или `$VAR` в bash) **не требуют** использования `SKIP`, так как слова `app.route`, `staticmethod` и `VAR` отсутствуют в списке зарезервированных ключевых слов Deck, и парсер безопасно пропустит их как текст.

`SKIP` — это **булевый флаг**, означающий: «весь текст от следующей строки до терминатора является payload'ом, отключи сканер ключевых слов».
- `SKIP` не принимает аргументов. Запись вида `@REPLACE 1 SKIP 3` является синтаксической ошибкой (`ERROR: SKIP takes no arguments`) и выявляется на этапе **Parsing**.
- Операция с `SKIP` автоматически становится последней в колоде. Любая операция после `SKIP` — ошибка.

## 12. Выбор маркера (`@` по умолчанию)

Основной маркер — `@`. Модель по умолчанию формирует колоды с `@APPLY`, `@REPLACE`, `@END`.

Альтернативный маркер — `$`. Используется, если payload содержит множественные валидные команды Deck с `@` на нулевой колонке (например, генерация документации по Deck).

Если payload содержит и `$`, и `@` на нулевой колонке, модель использует основной маркер (`@`), а конфликтную операцию ставит в конец колоды с модификатором `SKIP`.

---

## 13. Лимиты размера

- `MAX_DECK_LINES` (по умолчанию 5000) — суммарный лимит строк payload'а в колоде.
- `MAX_CREATE_LINES` (по умолчанию 50000) — лимит для внешнего `CREATE` (создание файла целиком — легитимно крупная операция).

## 14. Безопасность

Все файловые операции ограничены рамками рабочей директории (workspace root). Workspace устанавливается при запуске MCP-сервера (через аргумент `--workspace` или переменную окружения `WORKSPACE`) или использует CWD CLI. Попытки выхода за её пределы отклоняются на этапе **Validation**.

### 14.1. Атомарность записи на диск (Atomic Write для POSIX)

Файл на диске никогда не должен оказаться в промежуточном, поврежденном или пустом состоянии. Запись результата операции `APPLY` или `CREATE` выполняется по протоколу safe-write:

1. **Temp file в той же директории.** Временный файл создается строго в той же директории, что и целевой файл (через `tempfile.mkstemp(dir=target_dir)`). Это критично: системный вызов `rename` атомарен только в пределах одной точки монтирования.
2. **Write + fsync.** Данные записываются во временный файл, после чего вызывается `f.flush()` и `os.fsync()`, чтобы гарантировать сброс данных из page cache ОС на физический носитель.
3. **Сохранение метаданных.** Перед заменой считываются права доступа (`st_mode`) оригинального файла и применяются к временному файлу через `os.chmod()`.
4. **Атомарная замена.** Временный файл атомарно заменяет целевой через `os.replace()`.
5. **Откат при ошибке.** При любом исключении временный файл удаляется (`os.unlink`), а целевой файл остается нетронутым.

**Обработка Symlinks:** Если целевой путь является символической ссылкой, Deck обязан разрешить (resolve) её до абсолютного пути реального файла **до** создания временного файла. Атомарная замена всегда применяется к физическому файлу, а не к symlink.

**Запрещено:**
- Открывать целевой файл на запись напрямую (`open(..., 'w')`).
- Создавать временные файлы в системном `/tmp`.

## 16. Рекомендуемый профиль агента (для AGENTS.md / System Prompt)

Для оптимальной работы LLM с Deck, в системный промпт агента рекомендуется включить следующие жесткие правила:

- **Запрет на угадывание:** Никогда не применяй `REPLACE`/`DELETE` к файлу, который ты не читал через `GET` в текущей сессии.
- **Workflow поиска:** Сначала найди точные границы через `ripgrep` (для текста) или `ast-grep` (для функций/классов). Затем прочитай диапазон через `GET`. Только затем генерируй колоду.
- **Обязательность `<rev>`:** Никогда не пропускай `<rev>` в заголовке колоды.
- **Обработка Version Conflict:** Если получен `ERROR: version conflict — file changed`, это означает, что твой контекст устарел (Stale Context). ЗАПРЕЩЕНО пытаться угадать новые номера строк или переписывать файл целиком. ОБЯЗАТЕЛЬНО: остановись, выполни новый `GET` для получения актуального `<rev>` и структуры, и только затем пересгенерируй колоду.
- **Интеллектуальный SKIP:** Не используй `SKIP` для обычных декораторов (`@app.route`). Парсер умнее, чем ты думаешь. Используй `SKIP` только если генерируешь текст, содержащий literal-команды Deck (`@END`, `@REPLACE`), и ставь эту операцию в самый конец колоды.
